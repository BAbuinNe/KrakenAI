# KrakenAI — архитектура V2: проверка соответствия и ранжирование КП

Статус: проектная архитектура (не описание уже реализованного функционала). 2026-11-10.

## 1. Постановка задачи
На вход подаются ровно одно ТЗ и от 1 до 10 КП в пилоте. Система извлекает атомарные требования, сопоставляет доказательства из КП, классифицирует каждый пункт как PASS / FAIL / UNKNOWN, исключает КП с подтвержденным нарушением обязательного требования, а допустимые ранжирует по явно заданным весам критериев. Если нет ни одного допустимого, возвращает "рекомендация отсутствует"; неизвестный обязательный пункт означает "ожидает проверки", а не автоматическое исключение по несоответствию.

Главный выход: упорядоченный список ДОПУЩЕННЫХ КП + отдельные списки "отклонено" и "требует уточнения"; каждое решение содержит ссылки на фрагмент ТЗ и КП, причину и оценку.

## 2. Объем данных
Фактически измеренные файлы тестовой пары:
- Tz(2).docx — 10 677 байт, ~536 слов, 3 таблицы.
- Noutbuk1(2).docx — 6 867 байт, ~58 слов.
Это НЕ среднерыночная статистика: универсальной подтвержденной статистики размера/числа КП не найдено. До сбора корпуса не писать «средний размер КП = ...».

Текущие технические ограничения репозитория: 1 ТЗ + до 10 КП, до 5 МБ на файл, текст парсера ограничен 15 000 символами на файл. Потенциальная потеря длинных документов должна быть явно отмечена как риск; нельзя молча отрезать часть документа. Пилот следует нагрузочно тестировать по распределениям размера (P50/P90/P95), количества страниц, числу требований, времени анализа, использованию RAM, доле OCR.

## 3. Раздельная обработка форматов
PDF: извлечение текста и координат/номеров страниц, отдельная OCR-ветка для сканов. DOCX: параграфы/таблицы в порядке документа, сохранение номеров пунктов и ячеек. XLSX: лист, строка, колонка, тип и единица измерения. Изображения: OCR и проверка читаемости. Для всех — нормализация пробелов, единиц, диапазонов, десятичного разделителя без потери сырого доказательства. Получаем DocumentBlock(source_file,page_or_sheet,block_id,raw_text,normalized_text,kind).

## 4. Извлечение структуры
Каждое составное требование декомпозируется на атомарные:
Requirement(id, section, attribute, operator, threshold, unit, mandatory, weight, evidence_ref).
Например, «6 ядер, частота 2 ГГц» -> два требования. Данные КП:
OfferFact(attribute, value, unit, raw_text, evidence_ref).
LLM извлекает/предлагает структуру, но детерминированный валидатор проверяет число, диапазон, единицы и оператор; галлюцинации нельзя принимать без цитаты.

## 5. Семантический поиск и reranker
Для каждого требования сначала выполняем полнотекстовый / embedding-поиск по блокам КП; затем CrossEncoder получает ПАРУ (требование, фрагмент КП) и выдает score релевантности. Он ранжирует ФРАГМЕНТЫ-ДОКАЗАТЕЛЬСТВА, не коммерческие предложения. На коротких КП допустимо напрямую сопоставлять все блоки без отдельного bi-encoder. Reranker score НЕ вероятность соответствия техническому условию.
Для пилота можно использовать простой поисковый индекс и Gemini для объяснений; CrossEncoder — отдельная будущая ML-компонента с самостоятельной оценкой.

## 6. Классификация и проверка
Вердикт по атомарному требованию:
- PASS: подтверждено формализованной проверкой или доказанным семантическим соответствием;
- FAIL: найдено доказанное противоречие;
- UNKNOWN: параметр не найден, неоднозначен, разнится между фрагментами либо OCR ненадёжен.
Важно: отсутствие упоминания не означает FAIL. Для обязательных условий даже один FAIL -> REJECTED; без FAIL, но с UNKNOWN -> NEEDS_REVIEW; все обязательные PASS -> ELIGIBLE.

## 7. Бизнес-ранжирование КП
Применимо только к ELIGIBLE. Если ТЗ дает собственные веса и формулу (как в тестовом ТЗ, шкала 0/5/10), они имеют приоритет над универсальной эвристикой. Иначе пользователь подтверждает критерии и веса. Балл:
Score_i = sum_j (w_j * s_ij) / sum_j w_j,
где s_ij приведены к единой шкале 0..10, w_j неотрицательные. Неведомый критерий: НЕ заменять нулем автоматически; помечать как неполноту данных и не ранжировать как окончательный выбор, если критерий обязателен для вычисления результата. У равных баллов применяется tie-break из ТЗ (в примере — меньшая цена, только если цена подтверждена).

## 8. Метрики: качество системы, а не балл поставщика
Extraction: Precision/Recall/F1 атомарных требований и правильность извлечения числа/оператора/единицы.
Retrieval: Recall@K по заранее размеченным релевантным фрагментам.
Classification: macro-F1, confusion matrix, Accuracy (вторичная), отдельно Recall_FAIL и false-PASS rate по обязательным требованиям; неизвестные метки считаются отдельным классом.
Ranking: nDCG@3 (основная при размеченной градуированной релевантности), Precision@3, MRR при сценарии "первый приемлемый", Top-1 agreement с экспертным выбором.
End-to-end: доля верных решений о допуске, процент отчетов с проверяемыми доказательствами, частота ложного допуска, latency P50/P95, доля успешно обработанных документов.
Метрики считаются на раздельном экспертно размеченном тестовом наборе, не на боевых оценках системы и не на оценке Gemini самой себя. Разделять train/validation/test по закупочным кейсам, чтобы разные КП одного ТЗ не попадали в разные выборки.

## 9. Пример
ТЗ: CPU >=6 ядер, RAM >=16 ГБ, SSD >=512 ГБ, батарея >=50 Втч, USB-A >=2.
КП AeroLite14: 4 ядра, 8 ГБ, 256 ГБ, 42 Втч, USB-A=1.
Пять явных обязательных FAIL -> REJECTED. Заявленные подсветка, корпус, вес не компенсируют нарушения. У неизвестной цены нет нулевой цены или автоматически максимального балла. При одном КП рейтинга допущенных нет.

## 10. План испытаний
MVP: измерить базовый parser + deterministic rules на 30-50 закупочных кейсах; затем расширить до 100+ разнообразных кейсов и вручную разметить обязательные требования, факты и доказательства. Это цели по набору данных, а НЕ существующий корпус. Baselines: только ключевые слова, только rules, embeddings+rules, embeddings+cross-encoder+rules, LLM extraction+rules. Замерять точность и задержку; добавлять дорогостоящую компоненту лишь если ее выигрыш доказан.

ЭТА спецификация — целевая архитектура, а не утверждение, что embeddings, CrossEncoder и полноценная экспериментальная оценка реализованы.
